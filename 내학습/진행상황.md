### DB Phase 3 — 학습한 핵심과 보완

- 슈퍼키·후보키: 직원번호만으로 유일하게 구별할 수 있으므로 직원번호+이름에는 불필요한 이름이 있음. 처음 후보키로 답한 뒤 교정. 직원번호 단독은 후보키라고 설명.
- 기본키·대체키: 기본키로 선택하지 않은 후보키인 회사 이메일을 대체키로 맞힘.
- 복합키: 수강 기록에 과목번호+성적을 제안했다가, 성적 중복 반례로 교정. 학번+과목번호가 함께 필요하고, 성적을 더 붙인 조합은 불필요한 속성이 있는 슈퍼키라고 설명.
- 외래키·참조 무결성: C99가 고유하다는 이유만으로 주문 저장이 가능하다고 판단했다가, 참조 대상 고객 행이 먼저 존재해야 함을 설명으로 학습. 이후 존재하지 않는 과목을 참조하는 수강은 외래키 제약으로 거부된다고 맞힘. 조회는 과목명이 아니라 과목ID 기준이라는 용어를 보완.
- 참조 대상 삭제: 주문이 참조하는 고객의 삭제는 지정된 삭제 거부 규칙 때문에 불가하다고 설명. 주문 없는 고객 등록은 가능하다고 답했고, 테이블 분리 자체가 아니라 제약 방향 때문이라는 이유를 보완.
- 자연키·대리키: 이메일 대신 변경되지 않는 사용자 ID를 기본키로 선택한다고 근거까지 설명.
- 1:N 변환: 과목 테이블에 프로그램ID 외래키를 추가한다고 맞힘.
- N:M 변환: 수강 테이블에 학생ID·과목ID 외래키를 넣는 것은 맞혔으나 학생ID 단독 기본키를 제안함. 복합 기본키 하나가 두 속성으로 구성됨을 설명한 뒤, 같은 학생·같은 과목 조합의 중복은 거부된다고 맞힘.
- 자기 참조: 상사를 별도 테이블로 가정한 답을 같은 직원 테이블 참조 조건에 맞춰 보완. 상사ID는 같은 테이블의 직원ID를 참조하며, 한 상사는 여러 직원을 관리할 수 있어 반복 가능함을 학습.
- NULL: 상사가 없는 직원 허용 시 상사ID에 NOT NULL을 걸면 안 된다고 설명. 모듈 없음과 미분류를 같은 NULL로 표현하면 미분류 강의를 모듈 없는 강의로 잘못 집계한다고 설명.

### DB Phase 4 — 현재까지 확인한 내용

- 함수 종속 X→Y: 두 행의 X 값이 같으면 Y 값도 같아야 함. 같은 B에 다른 A는 B→A 위반, 서로 다른 B에 같은 A는 허용됨을 확인.
- 현재 데이터와 업무 규칙: 지금 이름이 모두 달라도 동명이인이 가능하므로 이름→학번을 일반 규칙으로 확정할 수 없다고 설명.
- 완전·부분 종속: 복합키 일부만으로 결정하면 부분 종속, 전체가 필요하면 완전 종속. 처음에는 중복 여부로 이유를 설명하거나 성적을 부분 종속으로 판정했다가 교정. 이후 상품번호만으로 상품명이 결정되므로 복합키에 부분 종속이라고 근거까지 설명.
- 이행 종속: 직원번호→부서번호→부서명을 연결함.
- 폐포: 집합에는 속성 이름을 각각 적고, 순서는 무관하며 중복은 한 번만 적음. 처음 속성 자체를 포함하고, 결정자의 모든 속성을 확보한 규칙만 적용함.
- 기호·표현: 학생은 기호와 용어가 처음이라 충분한 설명이 필요하다고 요청함. 순서 변경, 중복 정리, (C,E)의 공동 결정과 집합 원소 구별은 설명 부족을 보완한 것이며 그 자체를 새 오답으로 기록하지 않음.
- 10/14 독립 계산 결과: C⁺={C,A}; (C,E)⁺={C,E,D,A}; D→B 추가 후 (C,E)⁺={C,E,D,A,B}; E⁺={E}.
- 후보키 확인: (C,E)는 모든 속성을 결정하고 C 또는 E를 빼면 전체를 결정하지 못함. 슈퍼키라고 답한 것은 참이지만 후보키 여부 설명이 부족해 포함 관계를 보완함. 이후 (C,E,A)는 A가 불필요한 슈퍼키이고 A를 빼면 후보키라고 답함.
- 1NF는 정의와 첫 문제만 제시함. 아직 학생의 답을 받지 않았으며 1NF·2NF·3NF·BCNF 학습 완료로 처리하지 않음.

## 2026-10-16 DB 복습 및 게임프로그래밍 전환

- 오늘 예정된 DB 복습 11항목을 모두 다뤘다. 원래 표기 보존, 이름 대신 고유 번호로 연결, 분리 테이블의 연결 열, 엔티티와 식별자, 이력 필요 여부는 독립 정답을 받았다.

- 임곗값을 낮추는 것이 재현율을 높이려는 조정이라는 질문은 맞혔다. `probs[:, ____]`의 양성 열 선택에 `1:`라고 썼다. 이진분류의 클래스 순서 [0,1]에서는 1번 열부터 끝까지 선택하므로 양성 열을 고른 답으로 인정했다. `[:,1]`과 `[:,1:]`의 결과 차원 차이는 따로 평가하지 않았다.
- Binarizer의 threshold 매개변수와 fit_transform 역할을 설명했다. threshold 빈칸, 기준보다 클 때만 1이고 같거나 작으면 0이라는 설명 뒤 0.5 기준에 0.5 입력이 0이라는 문제를 맞혔다. precision_recall_curve에 최종 라벨 대신 양성 확률을 넣는 선택도 맞혔다.
- F1·ROC: F1은 정밀도와 재현율의 조화평균이며 한쪽이 매우 낮으면 높게 나오기 어렵다고 설명한 뒤 학생이 맞혔다. 단순 평균과의 차이는 AI가 보충했다. f1_score 입력은 최종 예측 라벨 pred로 맞혔다. 특이도와 FPR의 합이 1이라는 설명 뒤 특이도가 높으면 FPR은 낮다고 답했다. ROC는 x축 FPR·y축 TPR(재현율), AUC는 곡선 아래 면적이라고 설명했다. AUC 0.6보다 0.9가 좋다는 선택과 roc_auc_score의 양성 확률 입력을 맞혔다. ROC 축이나 roc_curve 반환값 자체의 별도 인출은 하지 않았다.

- 좌표·컴포넌트: 부모 월드 X=10, 자식 localPosition X=2에서 자식 월드 X도 2라고 답해 교정했고, 부모 X=20인 변형에서 자식 X=22를 맞혔다. GameObject는 부모만의 명칭이 아니며 부모와 자식 모두 개별 GameObject임을 설명했다. 기본 GetComponent가 자식도 찾는다고 답해 같은 GameObject만 검색한다고 교정했다. 이후 부모에만 Rigidbody2D가 있어도 자식의 기본 검색은 null이라는 혼합 문제를 맞혔다.
- 실행 함수·초기화: 처음에는 기억나지 않는다고 해 Awake/Start/Update/FixedUpdate를 설명했다. 이후 매 프레임 Update, 물리 업데이트의 일정 시간 간격 FixedUpdate, 첫 Update 전 한 번 Start를 직접 인출했다. 체력을 Update에서 100으로 대입하면 피해 후 다음 프레임에 다시 100이 된다고 설명했다. Awake의 참조·내부 값 준비 역할은 설명했으나 별도 인출은 하지 않았다. 비활성화가 필드 초기화가 아니라는 결론은 맞혔지만 처음에는 이유를 기억하지 못해 설명했다.
- 시간과 누적: 매 프레임 1만큼 이동하면 30/120 FPS에서 1초에 30/120만큼 이동한다고 독립 답변했다. deltaTime 방식은 1초에 6이라는 결론을 답했으나 코드 각 요소는 모른다고 해 transform.position, Vector3.right, speed, Time.deltaTime, +=를 설명했다. 시간 간격이 두 배이면 이동량이 증가한다고 답했으며 정확히 두 배라는 수치는 AI가 보충했다. 마지막 speed=8의 30/120 FPS 1초 이동량 질문은 사용자가 AI에게 답하라고 요청하여 AI가 설명했다. 이어 매 프레임 +=로 현재 위치에 누적되고 1초가 끝날 때 한꺼번에 더하는 것이 아니라는 설명을 했다. 이 마지막 계산과 누적 이해는 학생의 독립 답변으로 확인하지 않았다.
- 물리·이벤트: 통과 감지에 false라고 답했으나 어떤 설정을 말한 것인지는 특정하지 않았다. Collider2D 영역, Is Trigger 설정, 비활성화의 차이를 설명했다. Is Trigger를 꺼야 밟고 서는 바닥이 된다는 결론은 맞혔으며 막는 목적을 보충했다. 양쪽 Rigidbody2D가 없어도 Trigger 이벤트가 가능하다고 답해 최소 한쪽 필요 조건을 교정했다. 이후 어느 한쪽에 있으면 조건 충족, 코드로 겹치게 해도 양쪽 모두 없으면 이벤트 불가라는 이유를 맞혔다. 일반 바닥의 접촉을 Trigger라고 답했다가 뒤의 일반 벽 혼합 문제에서는 Collision이라고 답했다. 나머지 레이어·Body Type 조건이 올바르다고 가정했고, 2D/3D가 별도 물리 시스템임을 설명했다.
- 애니메이션 — 최우선 보완: Clip과 Controller의 내용/전환 구분은 처음에 대략 맞혔지만 확신이 없었다. 실제 재생 컴포넌트를 Animation Clip으로 답했고, 동일 Clip 반복을 Animator 설정 또는 Animator Controller로 반복 혼동했다. Clip=시간에 따른 변화 내용 에셋, Controller=상태·전환 에셋, Animator=실제 재생 컴포넌트의 관계를 여러 번 설명했다. 설명 후 세 역할을 각각 답했고 전환 수정은 Controller라고 답했으나, 다른 문제 뒤에 Loop Time을 다시 묻자 Animator 설정으로 재오답했다. 마지막에는 '애니메이터 클립의 루프타임'이라고 답해 정식 이름 Animation Clip을 교정했다. Loop Time이 Clip에 있다는 지연 인출은 아직 안정적으로 확인되지 않았다. Parameter 값 변경만으로 전환이 자동 생성되지 않으며 Controller의 연결·조건이 필요하다는 것은 직접 설명했다.
- 카메라: 처음 Size 증가 시 커질지 모른다고 했고 이후 화면 크기가 그대로라고 다시 답했다. Orthographic(표현 방식)과 Orthographic Size(보는 세로 범위의 절반), 실제 Scale과 화면 속 크기, 거리만 변경하는 경우를 구별해 설명했다. 최종 혼합 문제에서는 'Size 증가 → 범위 확대 → 실제 크기는 그대로지만 화면에서는 작게 보임'을 이유까지 정확히 답했다. 당일 재교정 결과이므로 간격 복습 성공으로 계산하지 않는다. Perspective와 Orthographic의 거리 효과는 설명했고 직교 거리 변경 문제는 맞혔다. Perspective의 Field of View 조절 항목은 이번에 별도 확인하지 않았다.
- 화면 구성·재사용: 창 이름 질문에서 Transform을 떠올리고 기억나지 않는다고 답해 Hierarchy와 Inspector를 설명했다. 이후 Inspector를 답하고 나중에는 부모·자식 관계 확인 창을 Hierarchy로 답했다. 오브젝트 풀의 기존 인스턴스 보관·재사용은 답했으며 생성/삭제 비용 절감 목적과 용량·수명에 따른 생성/삭제 가능성을 설명했다. Prefab과 같지 않냐는 질문에는 구성 에셋 재사용과 실제 인스턴스 재사용을 구별했다. 이후 매번 생성·삭제하는 것은 풀이 아니라 보관해서 재사용해야 한다고 직접 설명했다.
- 저장: 사용자가 오늘 여기까지 하고 내일 이동 중 한 시간 복습하는 계획을 문의하여 현재까지 기록했다. 진행 시간은 미측정이며 학생의 최종 세 줄 요약은 미작성이다. 학생 대신 요약 답안을 작성하지 않는다. 이번 세션의 PDF 전체 세부 항목이나 C# 전체 숙달을 완료 표시하지 않는다.
- 다음 시작: 10/20 게임 시험 전 복습은 (1) Animation Clip/Animator Controller/Animator와 Loop Time을 자료 없이 지연 인출, (2) deltaTime의 프레임당 이동·1초 누적을 새 숫자로 직접 계산, (3) Collision/Trigger·최소 한쪽 Rigidbody2D·Is Trigger 설정의 혼합 상황, (4) 월드/로컬·기본 GetComponent·Hierarchy/Inspector·카메라 Size 중 틀린 것만 재확인한다. 먼저 답을 받고 부족한 부분만 설명한다. 다른 과목의 기한이 된 복습을 이번 시험 직전 게임 복습에 끼워 넣지 않는다.
- 기존 DB·머신러닝·C# 반복문/return 복습 항목은 이번에 실제 확인하지 않았으므로 날짜와 상태를 변경하지 않았다. 게임 관련 당일 오답·인출 실패 항목은 1회차·다음 복습일 10/20으로 기록하고, 당일 교정으로 간격을 늘리지 않았다.

## 2026-10-20 게임프로그래밍 시험 직전 복습 — 최신 기록

- PDF 안의 내용만 사용하여 유니티 약점 중심으로 복습했다. 끝에 C# 코드 흐름 두 문제도 확인했다. 사용자가 계획한 한 시간과 실제 경과 시간을 혼동하지 않으며, 실제 공부 시간은 미측정이다. 반복 교정 응답을 합쳐 시험 총점으로 집계하지 않는다.

- 애니메이션: 첫 질문에 Animation Clip 에셋의 Loop Time을 독립적으로 답했다. 실제 재생 컴포넌트 질문에는 Transform이라고 오답해 Animator와 구별했다. 이후 Animator를 답했고, 애니메이커라는 표현은 학생이 명시적으로 오타라고 정정했으므로 추가 개념 오답으로 기록하지 않는다. Animator Controller가 전환 흐름을 담당함도 답했다. 최종 요약의 '얼마나 반복할지'는 Loop Time이 반복 횟수가 아니라 반복 여부를 정한다는 점으로 교정했다. 묶음 항목은 당일 오류가 있어 1회차·10/21 유지다.
- deltaTime·누적: speed=10, deltaTime=0.02에서 프레임당 이동량 0.2와 5회 누적 1을 직접 계산했다. 50/100 FPS의 1초 이동량 10은 맞혔으나, 이유를 '누적한 것도 아니기 때문에'라고 답해 두 경우 모두 매 프레임 누적되며 실행 횟수와 프레임당 거리의 차이가 상쇄됨을 설명했다. 이후 FPS 두 배면 프레임당 거리가 절반이라는 설명을 확인했다. 마지막 새 수치 speed=4·deltaTime=0.05·20프레임의 누적 거리는 4로 맞혔다. 최종 요약에서도 speed×deltaTime과 프레임당 누적을 언급했다. 당일 교정이 있어 1회차·10/21로 기록했다.
- 실행 함수: 인스턴스 초기화 때 참조·내부 값을 준비하는 함수에 Prefab이라고 답했다. Prefab 구성 에셋과 Awake 실행 함수를 구별해 설명했다. 설명 후 FixedUpdate·Start를 맞혔고, 다른 문제 뒤에도 Awake를 다시 인출했다. 이미 Start가 실행된 같은 인스턴스를 비활성화·재활성화만 해도 필드가 초기화되지는 않으며 별도 초기화 처리가 필요하다고 답했다. 새 스크립트 파일을 반드시 추가해야 하는 것은 아니며 기존 스크립트 안에 처리해도 된다고 보충했다. 실행 함수 항목은 1회차·10/21이다.
- 창·UI: Inspector는 바로 답했으나 Hierarchy 이름은 '하이퍼리드?'라고 불확실하게 답해 보충했고, 이후 별도 인출은 하지 않았다. Canvas 역할은 맞혔다. UI 위치·크기·앵커 컴포넌트는 처음에 기억나지 않는다고 했고, 이어진 버튼 문항에 Transform이라고 답했다. 학생이 해당 문장에 UI라는 조건을 다시 명시하지 않았다고 지적하여, 앞선 Canvas 문맥이 있었다는 점과 별개로 매 문항에서 조건을 명확히 적기로 했다. 이 애매한 문항만으로 추가 개념 오답을 확정하지 않는다. 이후 명시적으로 Canvas 기반 UI 버튼이라고 쓴 두 문항에는 RectTransform을 답했다. 복습큐에 RectTransform 인출 실패 항목을 추가하고 다음 날 재확인한다.
- 입력: 처음에는 하나의 Action에 여러 Binding을 연결해도 장치별 점프 코드를 따로 작성해야 한다고 답했다. 이미 Binding으로 연결된 조건을 짚고 입력 연결과 실제 행동 코드를 구별했다. 이후 Enter를 기존 점프 Action에 Binding으로 추가한다고 답했고, 마지막 혼합 문제에서는 같은 실행 함수를 사용해도 된다고 답했다. 학생의 '입력을 구별하고 싶으면 따로 해야 한다'는 조건에 무조건 점프 코드를 두 벌 만들 필요는 없다고 보충했다. 누른 순간 감지는 정확히 골랐다. 공유 코드 항목을 1회차·10/21로 추가했다.
- 재사용·UI 이벤트·코드 구조: 매번 Instantiate 후 Destroy하는 방식은 풀이 아니며 기존 객체를 보관해야 한다고 답했다. 풀에서도 필요에 따라 생성·삭제할 수 있음을 재안내했다. 버튼 이름·함수 이름이 같아도 On Click 등록이 필요함을 답했다. 정확히는 클릭 이벤트 자체가 없어지는 것이 아니라 등록된 호출 대상이 없다는 점을 보충했다. 외부 동작을 유지한 코드 정리는 리팩토링이라고 바로 답했다.

1. **Theory - Task, Start & End Event, Pools & Lanes** — 체크리스트 핵심 확인, 10/22 체크.

   - 누가 어떤 목적으로 읽는지에 따라 상세 수준을 조절한다고 설명했다. 신입 직원용 그림에 기술 세부사항이 과도한 사례에 학생은 '초보자가 보기 쉽게 순서가 정리된 그림'으로 바꿔야 한다고 답했다. 필요 없는 기술 세부사항과 필수 업무 단계의 보존은 AI가 보충했다.

   - 시스템 요구사항 모델에 18개가 있고 모든 독자가 BPMN 숙련자인 사례에서, 학생은 15개를 무조건 맞추는 것이 아니며 필요한 작업을 삭제하면 요구사항이 빠진다고 설명했다. 모든 독자의 숙련 조건 충족은 AI가 재강조했다. 학생이 그 조건까지 독립적으로 열거한 것으로 기록하지 않는다.
   - 문의 접수 → 유형 분류 → 담당팀 전달까지만 자동화하는 사례에서 종료 상태를 '담당팀 전달 확인'으로 답했다. AI가 '담당팀 전달이 완료됨'이라는 상태 표현으로 다듬었다. 고객 문제의 최종 해결까지 범위를 임의로 넓히지 않았다.
3. **How to choose an AI project** — 기준 설명과 첫 문제 제시만 진행, 미완료·미채점.
   - 좋은 후보는 기술적 가능성과 비즈니스 가치를 함께 만족해야 한다고 설명했다. 아래 선택 문제에는 아직 학생 답이 없다. 답을 대신 만들거나 오답 큐에 넣지 않는다.

- A2 후속 학생 설명: '도입 전에는 하나하나 학생 한명한명 눈으로 다 보면서 채점을 해야하고 나중에 한번 더 또 검토를 해야했는데 도입하고나서는 눈으로 다 보면서 채점하는 과정이 사라졌어 하지만 검토는 직접 한번 더 해야해 하지만 채점하는 과정이 매우 단축 됐어'. 이 응답으로 **검토까지 포함한 총 채점 시간 감소**를 이해했음을 확인. 최초 점수와 다른 사례 재시험 필요 상태는 유지.
- **A3 1/3:** 대량 계산 약점은 확인. 명단은 코드, 계산은 계산 도구, 안내문은 LLM으로 정확히 나눔. 입력 한도·행 누락 설명과 분담 기준 한 문장이 빠짐. 직접 제공된 이번 달 자료를 사용할 수 있다는 점과 모델의 지식 컷오프를 구별하도록 보충. 모범 답안 공개.
- **합계 2/9**, 상세는 `내학습/모의고사.md`. AI A4는 비용·모델 선택 문제만 제시했고 미응답. A5~A10, DB D1~D10, AI 요청 2단계는 미응시.

### 공통 3~6주차 — 체크리스트 20개 설명 완료, 독립 확인 미실시

### 다음 대화 재개 지점

1. 사용자가 공통을 이어가면 **C1을 다른 사례(예: 동아리방)로 독립 확인**한다. 장비 대여 C1의 모범 답안은 이미 열람했다. C2~C10은 미응시다. 모의 기록의 사례와 열람 표기를 확인하고 해당 문제·채점 파일을 짝지어 사용한다.
2. AI 문제를 이어가면 **A4 미응답**부터. A1~A3은 2점 이하이므로 오답 모드에서는 다른 사례로 재출제한다. A2 후속 설명 확인을 원래 점수의 회복으로 바꾸지 않는다.
3. 체크리스트 전체 범위와 실제 숙달은 구별한다. AI는 25강의 핵심 설명·사례를 한 번 다뤘지만 모든 세부 항목을 독립 서술로 검증하지 않았다. 이번 저장에서는 기존 체크박스를 일괄 완료로 바꾸지 않고 추가 독립 확인을 남긴다. DB·다른 과목 진도나 미실시 복습 날짜는 변경하지 않는다.
4. Phase별 요약은 대화에서 이미 받았다. 위 표는 AI가 정리한 진행 기록이며 학생의 최종 세 줄 요약 원문으로 가장하지 않는다. 새 종료 요약을 받지 않은 상태에서 사용자의 커밋·푸시 요청을 진행한다.
